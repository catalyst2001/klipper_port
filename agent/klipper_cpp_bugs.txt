A1. [toolhead.cpp] ОТСУТСТВИЕ CENTRIPETAL JUNCTION VELOCITY LIMIT
    Файл: trapq.cpp :: Move::calcJunctionV2()
    
    ПРОБЛЕМА: calcJunctionV2() вычисляет junction velocity только через
    junction deviation модель (jd * sinθ/2 / (1-sinθ/2) * accel). Отсутствует
    centripetal velocity limit = delta_v2 * 0.25 * tan(θ/2), который в
    оригинальном Klipper ограничивает скорость в junction-е для пологих
    поворотов (малые углы).
    
    ПОСЛЕДСТВИЕ: На пологих поворотах (cosθ ≈ -1, малый угол) junction
    deviation даёт высокий лимит, а centripetal — низкий. Без centripetal
    limit скорость завышена → высокие перегрузки, потеря шагов, рывки.
    
    ТАКЖЕ: Нет вычисления для предыдущего move (prev_move_jd_v2,
    prev_move_centripetal_v2). Если prev_move имеет сниженный accel (от
    kinematics check_move), junction будет рассчитан по accel текущего move,
    что тоже завышает скорость.
    
    ПРИОРИТЕТ: КРИТИЧЕСКИЙ
    ФАЙЛ: klipper_host/trapq.cpp, строки с calcJunctionV2

A2. [toolhead.cpp] НЕТ PRINT-TIME BACKPRESSURE
    Файл: toolhead.cpp :: moveAbsolute(), flush()
    
    ПРОБЛЕМА: m_nextPrintTime растёт без ограничений. При обработке
    большого gcode-файла toolhead генерирует тысячи moves и queue_step
    команд, отправляя их "в будущее" на десятки минут вперёд.
    
    ПОСЛЕДСТВИЕ:
    - Переполнение serial buffer / MCU command queue
    - Невозможно корректно приостановить печать (шаги уже в MCU)
    - При M112 (emergency stop) MCU уже заполнен командами на минуты вперёд
    - Рассинхронизация print_time и реального MCU clock
    
    В оригинале: _check_pause() блокирует gcode thread когда
    print_time - estimated_print_time > BUFFER_TIME_HIGH (1.0s)
    
    ПРИОРИТЕТ: КРИТИЧЕСКИЙ
    ФАЙЛ: klipper_host/toolhead.cpp

A3. [serial_port.cpp / klipper_mcu.cpp] НЕТ RETRANSMISSION
    Файл: klipper_mcu.cpp :: sendCommand()
    
    ПРОБЛЕМА: Команды отправляются через serial и не отслеживаются.
    Нет retransmission queue, нет ACK tracking, нет RTO estimation.
    При потере пакета (шум, buffer overflow) команда теряется безвозвратно.
    
    ПОСЛЕДСТВИЕ:
    - Потерянная queue_step = пропуск шагов
    - Потерянная config команда = MCU shutdown
    - Sequence number mismatch = потеря синхронизации
    
    В оригинале: C-level serialqueue ведёт retransmit queue, отслеживает
    ACK по sequence number, retransmit по timeout и duplicate ACK.
    
    ПРИОРИТЕТ: КРИТИЧЕСКИЙ
    ФАЙЛ: klipper_host/klipper_mcu.cpp, klipper_host/serial_port.cpp

--------

A4. [stepper.cpp] ХОМИНГ БЕЗ УСКОРЕНИЯ
    Файл: stepper.cpp :: PrinterRail::homeAxis()
    
    ПРОБЛЕМА: Хоминг выполняется queueStep(intervalTicks, maxSteps, 0) —
    constant velocity, мгновенный старт. Нет trapezoid profile.
    
    ПОСЛЕДСТВИЕ:
    - При homing_speed > stepper's instant-acceleration capability →
      пропуск шагов в первые мгновения
    - Stepper motor может не успеть разогнаться → дроп-ауты
    - Нет торможения после endstop trigger → увеличенный overtravel
    - Неточная позиция endstop (нет trig_pos коррекции)
    
    В оригинале: drip_move() проходит через полный planner, обеспечивая
    acceleration ramp при старте и deceleration при остановке.
    
    ПРИОРИТЕТ: ВЫСОКИЙ
    ФАЙЛ: klipper_host/stepper.cpp, строки ~258-336

A5. [toolhead.cpp] LOOKAHEAD FLUSH БЕЗ LAZY MODE
    Файл: toolhead.cpp :: lookaheadFlush()
    
    ПРОБЛЕМА: lookaheadFlush() всегда обрабатывает ВСЮ очередь.
    Последний move в batch-е всегда получает end_v=0 (complete stop).
    
    При flush по порогу 16 moves: каждые 16 moves принудительная остановка.
    Для arc сегментов (~1mm) это остановка каждые 16mm. Для прямых
    линий — каждые 16 G1 команд.
    
    ПОСЛЕДСТВИЕ:
    - Периодические полные остановки каждые 16 moves
    - Сильные артефакты на дугах и кривых
    - Снижение средней скорости печати
    
    В оригинале: lazy flush обрабатывает только moves до подтверждённого
    пика скорости, оставляя хвост очереди для дальнейшей оптимизации.
    
    ПРИОРИТЕТ: ВЫСОКИЙ
    ФАЙЛ: klipper_host/toolhead.cpp :: lookaheadFlush(), moveAbsolute()

B3. [stepper.cpp] HARDCODED ENDSTOP SAMPLE PARAMETERS
    Файл: stepper.cpp :: PrinterRail::homeAxis()
    
    ПРОБЛЕМА: restTime=0.01 hardcoded. В оригинале rest_time вычисляется

B4. [stepper.cpp] HOMING endstop POLLING С GOTO
    Файл: stepper.cpp :: MCU_endstop::home()
    
    ПРОБЛЕМА: Polling loop с timeout 5s использует goto done. Более серьёзно:
    trsync_state проверяется через processIncoming() в тесном цикле с

    ПОСЛЕДСТВИЕ: При сбое связи во время хоминга — зависание на 5 секунд,

    ПРИОРИТЕТ: СРЕДНИЙ
    ФАЙЛ: klipper_host/stepper.cpp :: MCU_endstop::home()

B5. [klipper_mcu.cpp] SEQUENCE SCANNING НЕЭФФЕКТИВНО
    Файл: klipper_mcu.cpp :: identify()
    
    ПРОБЛЕМА: При identify пробуются все 16 sequence номеров. Если MCU
    не отвечает (выключен/сломан), каждый sequence ждёт timeout * retries.
    С exponential backoff это может занять 16 * (10+20+40+80+160)ms = ~5s.
    
    ПОСЛЕДСТВИЕ: Медленный startup при проблемах с MCU. Не баг как таковой,
    но заметная задержка vs Python's serialqueue подход.
    
    ПРИОРИТЕТ: НИЗКИЙ

C1. [toolhead.cpp] generateSteps() — ORDER OF AXIS STEP SENDING
    
    ПРОБЛЕМА: Шаги генерируются и отправляются по осям последовательно
    (сначала все X, потом все Y, потом Z). Нет steppersync для координации.
    
    ПОСЛЕДСТВИЕ: На MCU шаги оси X окажутся в queue на десятки ms раньше
    шагов Y. Если MCU firmware имеет ограничение на глубину очереди —
    X-queue может переполниться до того, как начнут приходить Y-шаги.
    
    ПРИОРИТЕТ: СРЕДНИЙ
    ФАЙЛ: klipper_host/toolhead.cpp :: generateSteps()

--------

C2. [toolhead.cpp] generateShapedAxisSteps() — CONVERGENCE
    
    ПРОБЛЕМА: Secant/bisection solver для shaped steps имеет hardcoded
    лимит итераций (50). Если input shaper вызывает сложный non-monotonic
    profile (сильные осцилляции), solver может не сойтись.
    
    ПОСЛЕДСТВИЕ: Некоррктное step timing при extreme input shaper settings.
    В оригинале chelper-версия: те же ограничения, 50 итераций, но
    с дополнительной обработкой (itersolve_check_active).
    
    ПРИОРИТЕТ: НИЗКИЙ
    ФАЙЛ: klipper_host/toolhead.cpp

--------

C3. [clock_sync.cpp] THREAD SAFETY
    
    ПРОБЛЕМА: getClockEstimate() защищён mutex, но handleClockResponse()
    вызывается из main thread (синхронный processIncoming). При переходе
    к асинхронной модели potential race condition.
    
    Текущая реализация безопасна (однопоточная), но при рефакторинге в
    многопоточную модель — потребуется ревизия.
    
    ПРИОРИТЕТ: НИЗКИЙ (на будущее)

--------

C4. [gcode.cpp] ARC INTERPOLATION — RADIUS AVERAGING
    Файл: gcode.cpp :: cmdG2G3()
    
    ПРОБЛЕМА: Радиус вычисляется как среднее расстояний от центра до
    начальной и конечной точки: radius = (r1 + r2) / 2. При существенной
    разнице r1 и r2 (ошибка в I/J) дуга будет неточной без предупреждения.
    
    В оригинале (gcode_arcs.py): проверяет |r1-r2| < threshold и выдаёт
    ошибку при расхождении.
    
    ПРИОРИТЕТ: НИЗКИЙ
    ФАЙЛ: klipper_host/gcode.cpp :: cmdG2G3()

--------

C5. [klipper_mcu.cpp] processIncoming() — BUFFER HANDLING
    
    ПРОБЛЕМА: m_recvBuf растёт неограниченно (reserve 4096, но append
    без лимита). Если MCU шлёт мусор или данные приходят быстрее
    обработки — буфер может расти бесконечно.
    
    ПОСЛЕДСТВИЕ: Memory leak при corrupt serial data.
    
    ПРИОРИТЕТ: НИЗКИЙ
    ФАЙЛ: klipper_host/klipper_mcu.cpp :: processIncoming()

--------

C6. [tmc5160.cpp] NO WRITE VERIFICATION
    
    ПРОБЛЕМА: writeRegister() отправляет SPI данные без read-back
    верификации. В оригинале: запись → чтение → сравнение → retry до 5 раз.
    
    ПОСЛЕДСТВИЕ: Corrupt SPI transaction не обнаруживается. TMC5160 может
    работать с неверными настройками (ток, microstep count, stealthchop).
    
    ПРИОРИТЕТ: СРЕДНИЙ
    ФАЙЛ: klipper_host/tmc5160.cpp :: writeRegister()

--------

C7. [serial_port.cpp] TIMEOUT RESETTING ON EVERY READ
    
    ПРОБЛЕМА: read() вызывает SetCommTimeouts() на каждом вызове.
    Это syscall, и при высокой частоте polling (processIncoming в тесном
    цикле) — лишние kernel transitions.
    
    ПОСЛЕДСТВИЕ: Небольшое снижение производительности. Не баг, но
    неоптимальность.
    
    ПРИОРИТЕТ: НИЗКИЙ
    ФАЙЛ: klipper_host/serial_port.cpp :: read()

--------

C8. [klipper_config.cpp] COMMENT PARSING EDGE CASE
    
    ПРОБЛЕМА: parseFile() считает # комментарием только после пробела:
    "key: value # comment" → ok, но "key: value#nospace" → value включает #.
    Klipper Python ConfigParser стандартно не обрабатывает inline comments.
    
    ПОСЛЕДСТВИЕ: При пинах вида "PC0#" или значениях с # — некорректный
    парсинг. Маловероятно на практике, но edge case.
    
    ПРИОРИТЕТ: НИЗКИЙ

E1. [serial_port / klipper_mcu] ЗАВИСАНИЕ ПРИ ПЕРЕЗАГРУЗКЕ ПЛАТЫ

    - Автоматический disconnect с освобождением всех ресурсов сессии
    - Базовый reconnect flow (повторное открытие порта, re-identify, re-config)
    - Освобождение: serial handle, OID state, config commands, clock sync state
    
    ПРИОРИТЕТ: КРИТИЧЕСКИЙ (пользовательский опыт)
    ФАЙЛ: klipper_host/serial_port.cpp, klipper_host/klipper_mcu.cpp
